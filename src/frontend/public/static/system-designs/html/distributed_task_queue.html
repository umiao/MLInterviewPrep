7 Failure Scenarios (annotated on architecture)
X S1: Worker crash mid-execution
OOM / SIGKILL -- no graceful cleanup
Partial side-effects already committed
Broker timeout -> redeliver -> need idempotency
X S2: Ack lost (network drop)
Task succeeds, ack never reaches broker
Broker thinks task failed -> redelivers
Same idempotency requirement as S1
! S3: Timeout + dual execution
Worker A slow (GC, partition)
Broker redispatches to Worker B
Worker A recovers -- both execute
Fix: fencing tokens / lease IDs
! S4: Poison pill
Invalid params / logic bug
Fails -> retries -> fails forever
Fix: max retries + DLQ + backoff
X S5: Broker crash/restart
Redis RDB: in-flight tasks lost
Redis AOF: depends on fsync policy
RabbitMQ durable: survives restart
SQS: managed, always survives
! S6: Rolling deploy
v1 + v2 workers coexist
Serialization format mismatch
Fix: graceful drain + SIGTERM
! S7: Malformed payload
Empty or invalid task data submitted
Validate at enqueue (gateway) not just execute
Schema enforcement + reject or DLQ
+ Idempotency Toolkit

Broker Comparison

Best for: low-latency, loss-tolerant
RabbitMQ
AMQP protocol, rich routing
Durable queues + persistent msgs
Publisher confirms + consumer acks
Quorum queues (Raft-based HA)
Best for: reliable task routing
SQS (AWS)
Fully managed, auto-scaling
Visibility timeout for ack
DLQ built-in
At-least-once delivery
Best for: serverless / AWS-native
Kafka
Log-based, append-only
Consumer groups + offsets
Exactly-once (transactions)
High throughput, replay
Best for: event streaming + tasks

Retry Strategy
Exponential backoff + jitter
delay = base * 2^attempt + random(0, jitter)
Max retries -> DLQ routing
Error classification: transient vs permanent
Fencing & Leases
Fencing token per task assignment
Worker must present valid token on ack
Stale token rejected -> prevents dual-write
Lease TTL > expected execution time
